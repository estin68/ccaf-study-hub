01

Claude Models & Capabilities

Day 1 · ~30 min

Cues

  • What is Claude, and where can you use it?
  • Model tiers: Opus / Sonnet / Haiku — who picks which & why?
  • What is a context window?
  • Input vs output limits (token terms)?
  • What can Claude do — name 4 capability areas.
  • What are RPM / TPM / RPD?
  • Latest-model naming convention (<YYYY>-<MM>-<DD>)?

Notes — READ & RECALL

What is Claude? Anthropic's family of large language models, accessible via claude.ai (chat), the Claude Console / API (programmatic), and cloud marketplaces: AWS Bedrock and Google Vertex AI.

TierTrade-offTypical use
OpusHighest quality/reasoning; slower, pricierComplex analysis, deep reasoning, hard coding
SonnetBalanced — strong + fastDefault for most production workloads & agents
HaikuFastest & cheapest; light reasoningHigh-volume, simple tasks, classification

Context window = total tokens the model can process at once (system prompt + conversation history + tools + new input). It is the "working memory" of the model, much larger than output limits. Claude's long-context models handle ~200K tokens; some newer models reach 1M token-scale windows. Larger context means you can paste whole codebases or books.

Input vs output: context limits the input side (everything in the request). max_tokens caps the output side (a single response). A huge context does not mean the model can also output that much in one turn.

Capabilities: natural-language writing/analysis, coding (generation, debugging, refactoring), vision (images & PDFs), long-context reasoning, tool use & agentic workflows, structured output (JSON/XML).

Rate limits (per key/org): RPM = requests per minute, TPM = tokens per minute, RPD = requests per day. They gate raw throughput — not a model property, but a quota.

Model naming: dated versions like claude-3-5-sonnet-20241022 pin a snapshot; use alias like claude-sonnet-4 to get the latest stable in that tier.

Summary: Claude = Anthropic's LLM family on claude.ai, the API, Bedrock & Vertex. Pick the tier by cost/quality need: Opus = expert, Sonnet = default all-rounder, Haiku = fast & cheap. The context window is the model's whole-working-memory input limit; max_tokens limits each response's output.

Feynman lens — explain it simply

Claude is like a brilliant remote team you hire by the minute. An enormous context window means the whole project wiki fits on one desk at once; max_tokens is how long a single memo they hand you back may be. Opus is the slow senior partner, Sonnet the dependable SWE, Haiku the quick intern sorting tickets.

Analogy: hiring tiers ≠ intelligence, it's deliberation effort. Same assistant, more (Opus) or less (Haiku) time to think before answering.

Quick-check
  • 1. Highest-volume task (log classification) → which tier? → Haiku (fastest/cheapest).
  • 2. Paste a 150K-token codebase → what limit matters? → Input / context window.
  • 3. Which marketplaces host Claude? → AWS Bedrock, Google Vertex AI.
  • 4. RPM limits what? → Requests (not tokens) per minute.

LLM Core Concepts

Day 2 · ~30 min

Cues

  • What is a token? ~ how many per typical word?
  • Temperature — effect & sensible range?
  • Top-p — what does it control?
  • How do models "predict"? (next-token)
  • Why streaming & async?
  • Context window vs output — recap trap
  • How are LLMs trained (brief)?

Notes — READ & RECALL

Tokens are chunks of text the model reads & writes. ~0.75 token ≈ 1 word in English (a common 750→1,000-token-per-page rule of thumb). Billing, context, and rate limits are all token-based.

Temperature (0–1, default ~1) controls randomness / creativity. Lower (e.g., 0–0.3) = focused, deterministic, better for extraction & structured data; higher = more varied, creative brainstorming. For JSON / structured output, keep it low.

Top-p (nucleus sampling): sample only from the smallest set of tokens whose combined probability ≥ p. Lower top-p = more focused; higher = more diverse. Often you move one knob at a time (temperature OR top-p), not both.

Next-token prediction: Claude generates by repeatedly choosing the next most-probable token given all tokens so far. It has no "intent"; it produces the statistically most natural continuation — which is why clear prompts & examples dramatically shape output.

Streaming returns tokens as they're produced (better UX / perceived latency); async lets you manage multiple requests. Training = large-scale next-token learning on text + constitutional RLHF-style alignment to make Claude helpful & harmless.

Summary: LLMs predict the next token given all prior tokens; you control that prediction with sampling params. Temperature = creativity/randomness, top-p = diversity of candidate pool. Everything (cost, limits, context) is counted in tokens, and streaming/async shape production usage.

Feynman lens — explain it simply

Claude is an autocomplete on steroids: it just guesses the next best word, over and over. Temperature is how "surprising" its guesses may be (low = always picks the obvious word; high = sometimes picks something unusual). Top-p is like telling it "only choose among the top P% of likely options."

Analogy: autocomplete on your phone vs. an author. Same engine — the knobs and the prompt decide whether you get a terse memo or a novel.

Quick-check
  • 1. Get valid JSON — raise or lower temperature? → Lower (focused/deterministic).
  • 2. top-p does what? → Limits sampling to the top p-probability mass.
  • 3. ~How many tokens per English word? → ~0.75 token/word ≈ 1000 tokens/~750 words.
  • 4. Why streaming? → Tokens appear as generated → faster perceived response.
03

Prompt Engineering

Day 3 · ~40 min

Cues

  • Most important prompt skill (one word)?
  • System vs user role?
  • Few-shot / examples — why help?
  • Chain-of-thought & "role" prompting?
  • XML tags / delimiters — when to use?
  • Forcing valid JSON output?
  • How do excuses/ambiguity hurt output?

Notes — READ & RECALL

Clarity wins. The #1 rule: be specific and unambiguous. Vague input → confident-but-wrong output. Include role, task, format, and constraints.

System prompt sets global behavior (persona, rules, tone, guardrails) and persists across turns. User prompt is the current instruction/question. Anthropic encourages a "pretend you're a <role> — <task> — write in this format" structure.

Few-shot: provide 1–3 input→output examples. Claude pattern-matches them, improving format & style consistency far better than describing the format.

Chain-of-thought: ask Claude to reason step-by-step (or "think before answering") for complex tasks → more accurate. Role prompts ("You are a senior architect…") steer expertise/tone.

XML tags (<instructions>…</instructions>, <context>…</context>) separate data from instructions inside the prompt, reducing ambiguity — especially when the text itself contains instruction-like content. Never put untrusted data directly into the system prompt (prompt-injection risk).

Structured/JSON output: request "respond only with valid JSON" + show the schema and an example; use a low temperature; on the API you can request structured outputs that follow JSON Schema. Validate the response in code; never assume validity.

Summary: Good prompting = specific role + clear task + desired format + examples. Use system vs user roles, few-shot examples, chain-of-thought for reasoning, and XML tags/delimiters to separate data from instructions. For JSON, say so, show a schema, keep temperature low, and validate in code.

Feynman lens — explain it simply

Prompting is briefing a brilliant but literal contractor. If you say "make it better," they guess and usually guess wrong. If you say "you are the lead architect; here's the spec; respond as JSON with fields id and plan; here's one example," you get exactly the deliverable you want.

Analogy: an example is worth a thousand format descriptions. Claude copies what you show it, so always show, don't just describe.

Quick-check
  • 1. Best way to guarantee a format? → Provide a concrete example (few-shot).
  • 2. System vs user prompt? → System = global rules/behavior; user = current ask.
  • 3. How to get valid JSON? → "Respond only with JSON" + schema + low temp + validate.
  • 4. Why XML tags? → Separate data from instructions; cut ambiguity.

Claude Developer Platform

Day 4 · ~40 min

Cues

  • Where do you build & get API keys?
  • REST endpoint & key header?
  • Messages API roles?
  • Core request fields?
  • SDKs — Python/TS?
  • Why batch, caching & cost control?
  • Key security practice?

Notes — READ & RECALL

Claude Console is the web dashboard (claude.ai ≠ console: console.anthropic.com is where developers create API keys, monitor usage, and test). API keys are sk-ant-… and are used in the authorization: Bearer <key> header (or x-api-key).

Messages API is the primary interface: POST /v1/messages with roles system (optional top-level) and an array of user/assistant turns. Core fields: model, max_tokens (required), messages, plus optional temperature, top_p, system, tools, stream.

SDKs (Python anthropic, TypeScript @anthropic-ai/sdk) wrap auth, requests, streaming, & errors. Other SDKs (LangChain, etc.) exist but the official ones are the baseline.

Errors are HTTP codes: 400 bad/malformed request (also returned when an org/workspace spend cap is reached) · 401 auth (bad API key) · 402 billing problem · 403 permission denied · 404 not found · 429 rate limit (has retry-after + anthropic-ratelimit-* headers) · 500 server error · 529 overloaded. Good clients retry with exponential backoff + honor retry-after.

Prompt caching memoizes a stable prefix via cache_control to cut input-token cost & latency on repeated/big prompts; cache entries persist ~5 min (standard) or 1 hr (extended TTL). Vision/PDF: send images as base64, a URL, or a file_id; place images before the text question for best results. Claude can't identify named people or reliably detect AI-generated images, and complex medical scans need human review.

Production: costs are token-based; cache/shorter prompts and pick cheaper tiers for trivial work. Batch API lowers cost & raises throughput for non-urgent jobs (results in hours, ~50% cheaper). Security: keep keys server-side; scope via API keys in the console; never ship keys in client-side code.

Summary: Build in the Console, call /v1/messages with model + messages + max_tokens over HTTPS, using the official Python/TS SDK. Manage cost with tier choice, prompt size, and the batch endpoint; protect keys server-side and handle 4xx/5xx with retry/backoff.

Feynman lens — explain it simply

The Claude API is like ordering coffee at a counter: an HTTPS POST is your order, the API key is your ID card, model is which barista tier you want, max_tokens is how big a cup you'll accept, and messages is the conversation you hand over. The console is the kitchen where you get your card and watch your spend.

Analogy: batch = post a letter (cheap, slow, comes back ~a day later) vs. streaming = a live phone call (fast, token by token).

Quick-check
  • 1. Where do I create API keys? → Claude Console (console.anthropic.com).
  • 2. Required request field besides model & messages? → max_tokens.
  • 3. Message roles? → system (top), user, assistant.
  • 4. 429 = ? → Rate-limited / too many requests → back off & retry.
  • 5. Cheapest way to run a big non-urgent job? → Batch API (cheaper, ~24h).
  • 6. Service overloaded (status code)? → 529 → back off & retry (exponential).
  • 7. Same big prefix sent repeatedly? → Prompt caching — memoize the stable prefix to cut cost/latency.

Tool Use, MCP & Agents

Day 5 · ~45 min

Cues

  • What is tool use (function calling)?
  • The tool loop — steps?
  • What is MCP?
  • MCP server vs client role?
  • Example MCP tools?
  • What makes an agent?
  • Tool definition = name/desc/…?

Notes — READ & RECALL

Tool use lets Claude call functions you define (search, DB, calculator, code exec). You define tools with name, description (crucial — the model picks tools by it), and input input_schema (JSON Schema). Tools can be declared in the request with tools=[…].

The tool loop: ① You send message + tools → ② Claude replies with a tool_use block (it does not execute) → ③ Your code runs the tool and returns a tool_result user-turn → ④ send it back; Claude gives the final answer (or calls another tool). This loop repeats until done.

MCP (Model Context Protocol) is an open standard connecting models to tools/data. An MCP server exposes capabilities (tools, resources, prompts); an MCP client (the app — Claude, Agent SDK) connects. One standard speeds up integration & sharing.

Agents combine LLM + tools + a loop + environment access to pursue a goal, often autonomously across many steps. Claude Code / Agent SDK implement this. When you need decisions & actions (not just text), tools+agents are the architecture answer.

Security: with tools and agents, validate destinations, scope permissions, and treat call arguments as untrusted input for your code.

Summary: Tool use = give Claude defined functions; it emits tool_use, your app runs them, and you send tool_result back — repeat. MCP is the open standard for connecting models to tools/data. Agents are the loop of reasoning + tool calls toward a goal; strong descriptions & access control are what make them useful and safe.

Feynman lens — explain it simply

Tool use is like a chef who only cooks; you're the kitchen runner. The recipe says "grab tomatoes" (tool_use). You fetch, hand them over (tool_result). Only after you've fetched does the chef finish the plate. Claude never touches the fridge itself — it just asks, and your code is the hands.

Analogy: MCP is the universal power outlet — instead of wiring each appliance (tool) to each kitchen (app) differently, there's one standard socket. Agents = the chef who keeps deciding, step by step, what to do next until dinner is served.

Quick-check
  • 1. Who executes built-in tools Claude requests? → Your application code, not Claude.
  • 2. Order of the loop? → tool_use → your code runs → tool_result → reply.
  • 3. What is MCP? → Open standard for connecting models ↔ tools/data.
  • 4. Why is a tool's description important? → The model chooses which tool to call based on it.
  • 5. What makes a system an "agent"? → Reasoning loop + tools it can act on, toward a goal.

RAG & Context Engineering

Day 6 · ~45 min

Cues

  • What does RAG stand for? Why?
  • Embeddings — what are they of?
  • Vector search / similarity?
  • Chunking & why it matters?
  • How does RAG reduce hallucination?
  • Grounding cautions?
  • Retrieval vs. context engineering?

Notes — READ & RECALL

RAG = Retrieval-Augmented Generation. You retrieve relevant data from a knowledge base and inject it into the prompt, so Claude answers from your data rather than only memory. This enables private/up-to-date knowledge without retraining.

Embeddings convert text → dense numeric vectors that capture meaning. Vector search finds text whose embedding is "closest" (cosine/dot) to the query — i.e., semantically similar, far better than keyword match for meaning.

Pipeline: ① ingest docs → ② chunk into pieces → ③ embed chunks → ④ store in a vector DB → ⑤ at query time embed the question → ⑥ retrieve top-k → ⑦ place them in context with a grounding instruction → ⑧ Claude answers primarily from them, citing/quoting.

Chunking: split text into meaningful, sized chunks (with overlap) so retrieval finds precise, self-contained pieces — too-big chunks dilute relevance; too-small lose context.

Why it helps: grounds answers in real data → fewer confident fabrications ("hallucinations"), enables citation, and updates without retraining. Caveats: retrieval quality limits everything ("garbage in → garbage out"); poor/irrelevant retrieval can mislead more than no retrieval. Always instruct the model to say when info isn't present rather than guessing.

Summary: RAG = retrieve relevant chunks (via embeddings + vector search) into the prompt so Claude answers from your data with citations — reducing hallucination and keeping info fresh without retraining. Chunk well, embed for meaning, and let the model acknowledge when it doesn't know rather than fabricate.

Feynman lens — explain it simply

RAG is like giving an open-book test. Instead of making Claude answer from memory (where it may "remember" wrong), you place the relevant pages on the desk first. Embeddings are the smart filing-system index that finds "pages about X" by meaning, not just exact words. Retrieval is the TOC lookup; the generation is the answer written from the open book.

Analogy: memory-based LLM = a closed-book expert (fast, forgets, might bluff). RAG = same expert handed the right chapters (accurate, citable). The quality ceiling is how well you found the chapters.

Quick-check
  • 1. RAG stands for? → Retrieval-Augmented Generation.
  • 2. What are embeddings? → Dense numeric vectors capturing text meaning.
  • 3. Vector search finds …? → semantically similar chunks, not just keywords.
  • 4. Why chunk? → precise, self-contained retrieval units.
  • 5. Does RAG retrain the model? → No — it injects retrieved text into context.

Safety, Guardrails & Deployment

Day 7 · ~30 min

Cues

  • What is Constitutional AI?
  • Harm categories (concise)?
  • App-level guardrails?
  • Prompt injection? How to protect?
  • Deployment options (Bedrock/Vertex)?
  • Cost & latency levers?
  • Responsibilities of the architect?

Notes — READ & RECALL

Constitutional AI is Anthropic's alignment method: models are trained to be helpful, harmless, & honest using a written "constitution" of principles + feedback, instead of relying on human raters to detect harm. It aims to make Claude refuse harmful requests and be trustworthy by default.

Harm categories to architect against: violence/self-harm, sexual content, exploitation of children, hate/harassment/discrimination, illicit/illegal activity, weapons, deception (fraud), conflicts of interest (esp. in finance/abuse-of-trust contexts), and privacy. Anthropic provides safety/security resources & a Trust & Safety guidance for builders.

App-level guardrails: put strong, explicit rules in the system prompt; keep untrusted data out of the system prompt; treat tool-call arguments as untrusted; validate/whitelist actions; use a moderation step and content filters/safety settings; log & monitor.

Prompt injection / misuse: users may try to override instructions. Defense-in-depth: separate data from instructions (XML tags), never treat user content as trusted instructions, add rule rewordings, cap the power of systems around the model.

Deployment: the same Claude models exist via the Anthropic API as well as AWS Bedrock and Google Vertex AI. Drivers: existing cloud, data residency, procurement/atting, budgets, and unified tooling. Cost/latency levers = model tier, token counts, caching, batch, streaming.

Summary: Claude is aligned via Constitutional AI; architects add their own guardrails (system rules, validating untrusted data, moderation, minimal permissions). Deploy via the Anthropic API or managed clouds (Bedrock/Vertex). Safety is a shared responsibility — model defaults + your app-level controls.

Feynman lens — explain it simply

Constitutional AI is like giving the model a written code of conduct and training it to judge itself against it — so its "default reflexes" are to be helpful and refuse harm. Your job as architect is the bouncer + fire warden on top: how you handle user input and what powers you grant the system determine whether it's safe at scale.

Analogy: model = the trained employee (constitution); deployment = the workplace rules, doors that lock, and logbook (your guardrails, cloud choice, monitoring).

Quick-check
  • 1. Constitutional AI aims to make Claude …? → helpful, harmless & honest by construction.
  • 2. Where do dangerous directions belong? → out of user/data control → system prompt, not untrusted content.
  • 3. Main way to fight prompt-injection? → defense-in-depth: separate data, treat input as untrusted, limit power.
  • 4. Meaning of unknown-word "grounding" command? → Instruct model to say "not in context" rather than bluff.
  • 5. Managed deployment options? → Anthropic API, AWS Bedrock, Google Vertex AI.
